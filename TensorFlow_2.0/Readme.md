## 🎯 1. В чём суть задачи?

**Представьте:** у вас есть огромная книга (документ Википедии) и вопрос к ней. Ваша задача — найти **две вещи**:

1. **Длинный ответ (Long Answer)** — глава или раздел книги, где содержится ответ. Это может быть абзац, таблица или список.
2. **Короткий ответ (Short Answer)** — конкретная фраза внутри этого раздела, которая прямо отвечает на вопрос.

### Примеры:

**Вопрос:** "Кто написал роман 'Война и мир'?"

**В документе Википедии:**
```
Лев Николаевич Толстой (1828–1910) — русский писатель.

[Абзац-кандидат 1]
Одним из самых известных произведений Толстого является 
роман "Война и мир", написанный в период с 1863 по 1869 год.
Этот роман-эпопея описывает русское общество в эпоху войн 
против Наполеона...
```

**Ответ модели:**
- 🟦 **Long Answer:** весь абзац про "Войну и мир" (позиции в тексте 150:380)
- 🟩 **Short Answer:** фраза "Лев Николаевич Толстой" (позиции 220:245)

**Главная сложность:** документы могут быть огромными (до 400 000 слов!), и нейросеть не может "прочитать" весь документ за раз из-за ограничений памяти.

| example_id | PredictionString |

**Что означает "223:277"?** Это номера токенов (слов) в документе. Модель говорит: "Длинный ответ — это слова с 223 по 277". Пустая строка означает: "Ответа нет" (вопрос не имеет ответа в документе).

## 🧠 3. Ключевые понятия (объяснение для новичка)

### Что такое "токен" и почему текст делится на части?

> 💡 **Аналогия:** Представьте, что у вас очень длинный рулон обоев, а у вас есть рамка шириной 50 см. Чтобы рассмотреть весь узор, вы двигаете рамку по рулону шаг за шагом, и каждый раз видите новый кусок. 
> 
> BERT может обработать **только 512 токенов за раз** (примерно 300-400 слов). Если документ длиннее, его приходится "прокручивать" как рулон — это называется **sliding window** (скользящее окно).

### Что такое "Long Answer" vs "Short Answer"?

> 💡 **Аналогия:** Представьте, что вы в библиотеке ищете ответ на вопрос.
> - **Long Answer** = вы нашли **главу книги**, где обсуждается тема вопроса
> - **Short Answer** = вы нашли **конкретное предложение** внутри этой главы с прямым ответом
> 
> Иногда вопрос не имеет ответа — тогда оба ответа пустые ("impossible").

### Что такое BERT и почему именно он?

> 💡 **Аналогия:** BERT — это как **очень начитанный библиотекарь**, который прочитал миллионы книг и умеет понимать контекст слов. Если вы спросите "Что такое bank?", он поймёт по контексту — это речной берег или финансовое учреждение.
> 
> Для нашей задачи используется **BERT-large** — самая мощная версия с 340 миллионами параметров.

## ⚙️ 4. Как работает решение (сквозная аналогия)

### 📖 Эксперт №1: "Библиотекарь BERT" (нейросеть)

**Кто это:** Предобученная модель BERT-large, специально дообученная на 300 000 примерах из датасета Natural Questions от Google.

**Как он ищет ответ:**
1. Берёт вопрос и "окно" из 512 токенов документа
2. Для каждого слова в окне вычисляет три "оценки":
   - Вероятность, что это **начало** короткого ответа (`start_logit`)
   - Вероятность, что это **конец** короткого ответа (`end_logit`)
   - Вероятность, что это **длинный** ответ (`long_logit`)
3. Собирает топ-10 кандидатов для каждого типа
4. Выбирает лучший вариант, учитывая контекст

**Главная сложность:** один документ может быть длиннее 512 токенов. Решение — **нарезать документ на куски** и обработать каждый отдельно.

---

### 🔪 Что происходит с длинными документами?

**Проблема:** Документ из 50 000 слов. BERT помещает только 512 токенов.

**Решение — "скользящее окно" (sliding window):**
```
Документ:   [A A A A A A A A A A A A A A A A A A A A]
Окно 1:     [A A A A A A A A]
Окно 2:         [A A A A A A A A]   (с перекрытием)
Окно 3:             [A A A A A A A A]
```

Перекрытие нужно, чтобы ответ, находящийся на границе двух окон, не потерялся.

**Аналогия:** Вы читаете очень длинный свиток через маленькую прорезь. Чтобы не пропустить слово на стыке, вы немного возвращаетесь назад после каждого сдвига.

---

### 👥 Главный "хак" решения: 4 библиотекаря работают одновременно

В оригинальном решении один процесс обрабатывал весь тест **последовательно** — это занимало около часа. Мы ускорили это в **4 раза** через параллелизм.

**Как это работает:**

```
Документы 1-87  →  Библиотекарь 1 (GPU 0)
Документы 88-174 →  Библиотекарь 2 (GPU 0)
Документы 175-260 →  Библиотекарь 3 (GPU 1)
Документы 261-346 →  Библиотекарь 4 (GPU 1)
```

**Два процесса на одну видеокарту?** Да! BERT при инференсе (предсказании) использует GPU не на 100%. Два процесса умещаются на одной карте, работая одновременно.

**Результат:** 17 минут вместо часа.

---

### 🛡️ Эксперт №2: "Менеджер по времени" (бюджетный контролёр)

Это самая важная часть решения. Kaggle жёстко ограничивает время выполнения ноутбука. Если ваш код работает 9 часов — он автоматически убивается, и вы не получаете результат.

**Как работает менеджер:**

```python
BUDGET = 2 часа 40 минут  # безопасный лимит
MARGIN = 20 минут         # запас на финализацию
```

**Сценарии:**

| Ситуация | Что делает менеджер |
| :--- | :--- |
| Осталось много времени | Запускает следующий кусок теста |
| Осталось < 20 минут | **Не запускает** новые куски — не успеют |
| Время вышло, процесс ещё работает | **Убивает** процесс (kill) |
| Кусок не обработан | Добавляет **пустую строку** в submission.csv |

**Зачем пустые ответы?** Kaggle принимает submission.csv, если в нём все `example_id` присутствуют. Пустая строка = "ответа нет". Это лучше, чем сломанный файл с ошибкой.

**Аналогия:** Вы пишете эссе на экзамене. За 10 минут до конца вы не начинаете новый абзац, а дописываете текущий и ставите точку. Лучше сдать неполное, но оформленное эссе, чем не сдать ничего.

## 🚀 5. Три главных инженерных решения

### 🔧 Решение №1: Проверка окружения в начале

**Проблема:** Kaggle меняет пути к файлам. Старые ноутбуки не работают, потому что `../input/...` больше не существует.

**Решение:** Автоматический поиск нужных файлов (токенизаторы, веса BERT, кэш) и создание символических ссылок в `/tmp/inp/`. Плюс проверка:
- Python 3.6 (требуется для TF 2.0)
- Подключены ли все 6 нужных датасетов
- Есть ли GPU

Если что-то не так — скрипт **громко ругается** и показывает, что делать.

---

### 🔧 Решение №2: Умная нарезка теста

**Проблема:** Нельзя просто взять и поделить документы поровну, потому что они разной длины.

**Решение:** 
- Документы делятся на **примерно равные куски** (по ~87 документов)
- Каждый кусок обрабатывается отдельным процессом
- В конце результаты **склеиваются** по `example_id`

Если какой-то кусок упал (например, из-за OOM — не хватило памяти), он автоматически **перезапускается** один раз.

---

### 🔧 Решение №3: Валидация перед отправкой

Перед тем как сохранить `submission.csv`, код проверяет:
1. **Уникальность** `example_id` (не должно быть дублей)
2. **Соответствие** `sample_submission.csv` (все ID на месте)
3. **Формат** ответов (только числа вида "start:end" или пустая строка)
4. **Статистика**: сколько непустых длинных и коротких ответов

Если проверка не проходит — скрипт ругается, и вы не потеряете время на подачу невалидного файла.

## 🎓 8. Ответы на каверзные вопросы преподавателя

**В: "Почему BERT-large, а не более современные модели (RoBERTa, DeBERTa)?"**
О: На момент проведения соревнования (2020 год) BERT-large был state-of-the-art для QA. Современные модели дают прирост в 1-2%, но требуют переписывания кода и новых весов. Для данной задачи прирост был бы незначительным.

**В: "Почему именно 2 процесса на GPU, а не больше?"**
О: BERT при инференсе использует GPU не на 100% — около 50-60%. Два процесса умещаются на одной карте, а три уже конфликтуют за память. Это было проверено экспериментально.

**В: "Что будет, если тест увеличится до 1000 документов?"**
О: Текущий подход масштабируется линейно. Нужно просто увеличить `MAX_SHARD_DOCS` или добавить видеокарт. Архитектура поддерживает любое количество параллельных процессов.

**В: "Почему нельзя просто увеличить длину окна BERT до 4096 токенов (Longformer)?"**
О: В 2020 году Longformer ещё не был широко распространён, и для него не было предобученных весов на Natural Questions. BERT-large был оптимальным выбором с готовыми весами.

**В: "Что такое F1-мера в контексте QA?"**
О: Для каждого ответа считается:
- **Precision** = какая доля предсказанных слов действительно входит в правильный ответ
- **Recall** = какая доля слов правильного ответа была найдена

F1 — гармоническое среднее Precision и Recall. Если модель выделила чуть больше или чуть меньше слов, чем нужно, F1 всё равно будет высоким. Это мягче, чем строгое совпадение.

**В: "Почему некоторые ответы пустые?"**
О: Это означает, что модель уверена: **ответа нет** в документе. BERT предсказывает специальный токен `[CLS]` как "null answer". Если его оценка выше, чем у любого реального ответа, модель выдаёт пустую строку. Это важная функция — не каждый вопрос имеет ответ в конкретной статье Википедии.

## 💻 9. Как запустить этот код

### Требования на Kaggle:

1. **Settings → Accelerator:** GPU T4 x2 (или P100)
2. **Settings → Environment:** Pin to original environment (Python 3.6, TF 2.0)
3. **Settings → Internet:** Off (не требуется, всё в датасетах)
4. **Add Input:** Подключить 6 датасетов:
   - `tokenizers-repo`
   - `sacremoses-repo`
   - `transformers-repo`
   - `transformers-cache`
   - `nq-bert-uncased-68`
   - `tensorflow2-question-answering` (данные соревнования)

### Запуск:

```python
# Просто Run All (Cell → Run All)
# Весь код сам:
# 1. Проверит окружение
# 2. Установит нужные пакеты из .whl
# 3. Нарежет тест на куски
# 4. Запустит 4 параллельных процесса
# 5. Соберёт результат в submission.csv
# 6. Проверит файл на валидность
```

### Переменные для тонкой настройки:

| Переменная | По умолчанию | Что делает |
| :--- | :---: | :--- |
| `BUDGET` | 2ч 40м | Лимит времени |
| `MAX_SHARD_DOCS` | 100 | Максимум документов в одном куске |
| `MAX_WORDS` | 0 (без обрезки) | Можно обрезать длинные документы для скорости |

## 💡 Что отличает это решение от обычного бейзлайна:

1. **Параллелизм:** вместо 1 процесса — 4, на 2 GPU
2. **Страховка по времени:** никогда не потеряете submission из-за таймаута
3. **Авто-проверка окружения:** скрипт сам скажет, что у вас не подключено
4. **Устойчивость к ошибкам:** упавший кусок перезапустится автоматически
5. **Без интернета:** всё работает офлайн, веса моделей в датасетах

Это решение — пример того, как **инженерный подход** (параллелизм, контроль времени, проверки) может значительно улучшить даже стандартный бейзлайн, не меняя саму модель.
