# 📚 NLP Question Answering — математика и логика (markdown-версия)

## 1. Постановка задачи в цифрах

**Дано:**
- Документ длиной до **400 000 токенов** (слов)
- Вопрос длиной до **64 токенов**
- Модель принимает максимум **512 токенов** на вход

**Найти:**
- **Короткий ответ:** пару чисел `старт:конец` (позиции слов в документе)
- **Длинный ответ:** пару чисел `старт_абзаца:конец_абзаца` (границы абзаца из разрешённого списка)
- Либо **пустую строку**, если ответа в документе нет

---

## 2. Математика модели: три линейные головы

### Что делает BERT с входом

Вход форматируется так:

```
[CLS] w1 w2 ... wk [SEP] t1 t2 ... tm [SEP]
  ↑    вопрос          ↑     документ        ↑
```

После 24 слоёв трансформера каждый токен имеет скрытое представление:

```
h_i — вектор из 1024 чисел, для i = 0, 1, ..., L-1
где L — длина последовательности (до 512)
а h_0 соответствует токену [CLS]
```

### Три головы — это просто линейные преобразования

**Голова 1 (начало короткого ответа):** для каждого токена считается скаляр

```
s_i = W_s · h_i + b_s
где W_s — вектор весов из 1024 чисел
```

**Голова 2 (конец короткого ответа):**

```
e_i = W_e · h_i + b_e
где W_e — вектор весов из 1024 чисел
```

**Голова 3 (начало длинного ответа / абзаца):**

```
l_i = W_l · h_i + b_l
где W_l — вектор весов из 1024 чисел
```

Каждая голова — это **один плотный слой** `Dense(1024 → 1)`. Никакой магии: скалярное произведение вектора токена на вектор весов. Чем больше результат — тем выше уверенность модели, что данный токен является началом/концом ответа.

**Итого на выходе модели для каждого токена — три числа: `s_i`, `e_i`, `l_i`.**

### Соответствие коду

```python
class TFBertForNaturalQuestionAnswering:
    def __init__(self, config):
        self.bert = TFBertMainLayer(config)
        # ГОЛОВА 1+2: короткий ответ (начало и конец)
        self.qa_outputs = Dense(config.num_labels)   # num_labels = 2
        # ГОЛОВА 3: длинный ответ
        self.long_outputs = Dense(1)

    def call(self, inputs):
        sequence_output = self.bert(inputs)[0]       # [batch, seq_len, 1024]
        logits = self.qa_outputs(sequence_output)    # [batch, seq_len, 2]
        start_logits, end_logits = split(logits)     # по [batch, seq_len]
        long_logits = self.long_outputs(sequence_output)  # [batch, seq_len]
        return start_logits, end_logits, long_logits
```

## 3. Механизм внимания внутри трансформера

Это единственное место, где есть настоящая матричная математика.

### Формула внимания

Для каждой из 16 голов вычисляется:

```
Attention(Q, K, V) = softmax( Q · K^T / sqrt(d_k) ) · V

где:
  Q, K, V — матрицы размера [L × d_k]
  d_k = 1024 / 16 = 64 (размерность каждой головы)
  sqrt(d_k) = 8
```

**Зачем делить на `sqrt(d_k) = 8`:** чтобы значения в экспоненте не улетали в бесконечность. Иначе `softmax` превращается в `one-hot` и градиенты пропадают.

### Что это значит физически

Элемент `A[i][j]` матрицы внимания показывает, **насколько токен `i` должен опираться на токен `j`**.

Пример для слова "взрыв" в фразе "взрыв на заводе, эвакуация":

| | взрыв | на | заводе | эвакуация |
| :--- | :---: | :---: | :---: | :---: |
| **взрыв** | 0.15 | 0.05 | **0.45** | **0.35** |

Слово "взрыв" сильно связано с "заводе" и "эвакуация" → модель понимает контекст реального события.

### Итог одного слоя

Все 16 голов конкатенируются и проецируются:

```
MultiHead(Q, K, V) = Concat(head_1, head_2, ..., head_16) · W_O

Размер: [16 × 64] = [1024]
```

Результат снова вектор размера 1024 — такой же размер, как на входе, поэтому слои можно ставить друг за другом (24 раза).

## 4. Ключевая проблема: документ длиннее 512 токенов

### Математика скользящего окна

Параметры из кода:

```
max_seq_length    = 512
max_query_length  = 64
special_tokens    = 3   ([CLS], [SEP], [SEP])
```

Максимум токенов документа в одном окне:

```
max_tokens_for_doc = 512 - 64 - 3 = 445
```

Шаг скольжения:

```
doc_stride = 256
```

### Формула генерации окон

```
Окно 0: [0, 445)
Окно 1: [256, 701)
Окно 2: [512, 957)
...
Окно k: [256·k, 256·k + 445)
```

Общая формула:

```
Окно_k = [ 256·k ,  min(256·k + 445, длина_документа) )
```

Количество окон для документа длиной N:

```
num_windows = ceil( (N - 445) / 256 ) + 1
```

Для документа из 100 000 токенов: примерно **390 окон**.

**Перекрытие между соседними окнами:**

```
перекрытие = 445 - 256 = 189 токенов
```

Это гарантирует, что ответ на границе двух окон не потеряется.

### Выбор лучшего окна для токена

Один токен может попасть в несколько окон. Нужно выбрать **одно** окно, в котором этот токен имеет максимальный контекст. Формула из кода:

```
score(окно, токен) = min(левый_контекст, правый_контекст) + 0.01 · длина_окна

где:
  левый_контекст  = позиция_токена - начало_окна
  правый_контекст = конец_окна - позиция_токена
```

**Логика:** минимум из левого и правого контекста = гарантированное количество токенов с обеих сторон. Чем оно больше — тем лучше модель "видит" окружение слова.

Пример для токена на позиции 300:

| Окно | Диапазон | Левый контекст | Правый контекст | Минимум |
| :---: | :---: | :---: | :---: | :---: |
| Окно 0 | [0, 445) | 300 | 144 | **144** |
| Окно 1 | [256, 701) | 44 | 400 | **44** |

Токен 300 → **Окно 0** (144 > 44).

## 5. Алгоритм выбора ответа из логитов

После прогона всех окон через модель у нас есть массивы `s`, `e`, `l` для каждого окна. Дальше — чистая комбинаторика.

### Шаг 1: кандидаты из каждого окна

Для каждого окна берём **топ-10** позиций по каждому вектору:

```
S_top = argsort(s)[-10:]   # топ-10 начал
E_top = argsort(e)[-10:]   # топ-10 концов
L_top = argsort(l)[-10:]   # топ-10 абзацев
```

Параметр `n_best_size = 10`.

### Шаг 2: перебор пар для короткого ответа

Для каждой пары `(i, j)` из `S_top × E_top` проверяем **фильтры валидности**:

```
1. i <= j                          (начало не может быть после конца)
2. j - i + 1 <= 30                 (ответ не длиннее 30 токенов)
3. Оба токена отображаются на реальные слова
   (не [CLS], не [SEP], не паддинг)
4. Оба токена находятся в своём лучшем окне
   (token_is_max_context = True)
```

Для каждой валидной пары считается **суммарный скор**:

```
score(i, j) = s_i + e_j
```

### Шаг 3: сортировка и выбор лучшего

Все валидные пары из всех окон сортируются по убыванию скора:

```
(i*, j*) = argmax по всем (i, j) из [ s_i + e_j ]
```

Это и есть **лучший ненулевой кандидат**.

### Шаг 4: решение "пустой ответ или реальный"

Вот здесь ключевая логика. Скор пустого ответа = логиты токена `[CLS]` (индекс 0):

```
score_null = s_0 + e_0
```

Разница:

```
delta_short = score_null - (s_i* + e_j*)
```

**Правило:**

```
если delta_short > 0:
    ответ = "" (пустая строка)
иначе:
    ответ = слова [i*, j*]
```

**Смысл:** если логит `[CLS]` больше суммы логитов лучшего реального ответа → модель уверена, что **ответа в документе нет**. Порог = 0.0 (жёсткое сравнение).

Аналогично для длинного ответа, но там только один логит:

```
delta_long = l_0 - l_k*
```

### Соответствие коду

```python
# Оценка "пустого ответа" = логиты токена [CLS] (индекс 0)
start_score_null = result.start_logits[0]
end_score_null   = result.end_logits[0]
short_score_null = start_score_null + end_score_null

# Лучший реальный ответ
short_best_score = best_non_null.start_logit + best_non_null.end_logit

# Разница
short_score_diff = short_score_null - short_best_score

# Порог (в коде = 0.0)
if short_score_diff > short_null_score_diff_threshold:
    final_pred = ""       # ПУСТОЙ ОТВЕТ
else:
    final_pred = best_non_null.text   # РЕАЛЬНЫЙ ОТВЕТ
```

## 6. Преобразование токенов обратно в позиции слов

Токенизатор разбивает слова на субтокены:

```
Оригинал:   "Толстой написал"
Субтокены:  "То" "##лстой" "напи" "##сал"
```

Поэтому нужен **маппинг** `token_to_orig_map`:

```
token_to_orig_map[позиция_субтокена] = позиция_оригинального_слова
```

Финальный короткий ответ:

```
PredictionString = token_to_orig_map[i*] : (token_to_orig_map[j*] + 1)
```

**Почему +1?** Потому что в формате соревнования правая граница **невключительна**: `"224:227"` означает слова 224, 225, 226 (три слова).

### Длинный ответ: поиск ближайшего кандидата

Длинный ответ обязан начинаться с одного из **разрешённых абзацев** (`long_answer_candidates` из исходного теста). Модель предсказывает только токен начала `k*`. Ищем совпадение:

```
long_token = token_to_orig_map[k*]

для каждого кандидата (c_start, c_end):
    если c_start == long_token:
        ответ = c_start : c_end
        стоп
```

Если точного совпадения нет — кандидат **отбрасывается** (длинный ответ = пустая строка). В логах видно: `Found 253 of 346` — часть длинных ответов не находится.

## 7. Математика параллельной обработки

### Деление на куски

Тест: 346 документов. Количество процессов:

```
W = min(4, 2 · num_GPU) = 4   (при 2 GPU)
```

Документов в одном куске:

```
shard_docs = max( 50, min(100, ceil(346 / 4)) ) = 87
```

Количество кусков: `ceil(346 / 87) = 4`.

Распределение по GPU (2 процесса на карту):

| Кусок | Документы | GPU |
| :---: | :---: | :---: |
| 0 | 1–87 | GPU 0 |
| 1 | 88–174 | GPU 1 |
| 2 | 175–261 | GPU 0 |
| 3 | 262–346 | GPU 1 |

### Бюджет времени

Пусть `T0` — момент старта ноутбука. Определены два порога:

```
BUDGET = T0 + 9600 сек    (2 часа 40 минут)
DEADLINE_START = BUDGET - 1200 сек    (за 20 минут до дедлайна)
```

**Логика управления:**

```
Новый кусок стартует ТОЛЬКО если:
    есть незапущенные куски
    И  текущее_время < DEADLINE_START

Если текущее_время > BUDGET:
    все ещё работающие процессы УБИВАЮТСЯ (p.kill())
    их документы получат пустые ответы
```

### Сборка финального файла

```
итог = concat(submission_1, submission_2, submission_3, submission_4)

потом:
1. Удаление дубликатов по example_id
2. Поиск пропусков:  miss = sample_ids - итог_ids
3. Пропуски заполняются пустыми строками
4. Сортировка по example_id
```

**Инвариант:** финальный файл **всегда** содержит все 692 строки из `sample_submission.csv` (346 документов × 2 типа ответа), даже если часть процессов упала.

## 9. Вся логика пайплайна в одной схеме

```
ВХОД: документ (100 000 токенов) + вопрос (10 токенов)
  │
  ├─► Токенизация: слова → субтокены
  │
  ├─► Разбиение на окна по 512 токенов (шаг 256)
  │      Количество окон: ~390 для такого документа
  │
  ├─► Каждое окно → BERT → три вектора логитов:
  │      s_i (начало короткого)
  │      e_i (конец короткого)
  │      l_i (начало абзаца)
  │
  ├─► Из каждого окна: топ-10 начал × топ-10 концов
  │      Фильтры: длина ≤ 30, начало ≤ конец, реальные слова
  │
  ├─► Все пары из всех окон → сортировка по (s_i + e_j)
  │
  ├─► Сравнение с [CLS]:
  │      если (s_0 + e_0) - (s_i* + e_j*) > 0 → пустой ответ
  │
  ├─► Маппинг субтокенов → оригинальные слова
  │
  ├─► Короткий ответ:  "старт : конец+1"
  │   Длинный ответ:   поиск кандидата с совпадающим началом
  │
  └─► ВЫХОД: две строки в submission.csv
```

## 11. Ответы на глубокие вопросы преподавателя

**В: "Почему модель предсказывает логиты, а не сразу текст?"**

О: Потому что BERT работает с **фиксированным словарём токенов** (30 522 токена для BERT). Он не может генерировать произвольный текст — только указывать на позиции во входном тексте. Это превращает задачу генерации в задачу **классификации позиций**.

**В: "Почему [CLS] токен означает 'нет ответа'?"**

О: `[CLS]` — специальный токен, который не является частью реального текста. При обучении для примеров **без ответа** правильная позиция начала/конца ставится именно на `[CLS]`. Модель учится: "Если я не вижу ответа, я должна дать максимальный логит для [CLS]".

**В: "Почему порог для пустого ответа = 0.0, а не что-то другое?"**

О: Порог 0.0 означает: "Предсказывай пустой ответ только если [CLS] **строго лучше** лучшего реального ответа". Это консервативный подход — мы предпочитаем дать хоть какой-то ответ, чем ошибочно сказать "ответа нет".

**В: "Почему два процесса на одной GPU?"**

О: При инференсе BERT использует GPU не на 100% (примерно 50-60% загрузки). Второй процесс использует свободные вычислительные блоки. Памяти хватает: модель занимает ~1.5 ГБ, а на T4 16 ГБ.

**В: "Что такое `token_type_ids` и зачем они нужны?"**

О: Это вектор, который говорит BERT, какая часть входа — вопрос, а какая — документ:

```
[CLS] вопрос [SEP] документ [SEP]
  0     0      0     1       1
```

BERT использует эту информацию, чтобы по-разному обрабатывать вопрос и контекст.

**В: "Почему `MAX_WORDS = 0` (без обрезки документов)?"**

О: Обрезка до 30 000 слов экономит время, но **теряет ответы**, которые находятся в конце документа. В данном решении выбрана максимальная точность, а скорость достигается параллелизмом.

## 🎯 1. В чём суть задачи?

**Представьте:** вы библиотекарь. Вам приносят **огромную книгу** (до 400 000 слов!) и задают вопрос. Ваша работа — найти:

1. **Главу**, где обсуждается тема вопроса (это **длинный ответ**)
2. **Конкретное предложение** внутри этой главы (это **короткий ответ**)

### Пример:

**Вопрос:** "Кто написал роман 'Война и мир'?"

**В документе Википедии:**
```
Лев Николаевич Толстой (1828–1910) — русский писатель.

[Абзац-кандидат]
Одним из самых известных произведений Толстого является
роман "Война и мир", написанный в период с 1863 по 1869 год.
Этот роман-эпопея описывает русское общество в эпоху войн
против Наполеона...
```

**Ответ модели:**
- 🟦 **Длинный ответ:** весь абзац про "Войну и мир" (позиции 223:277)
- 🟩 **Короткий ответ:** фраза "Лев Николаевич Толстой" (позиции 224:226)

### Главная сложность

Документы огромные — до **400 000 слов**, а нейросеть может "прочитать" только **512 токенов за раз**. Это как читать книгу через маленькую замочную скважину.

| Ситуация | Последствие | Серьёзность |
| :--- | :--- | :---: |
| Модель нашла не тот абзац | Оценка частично снижена | 🟡 Средняя |
| Модель нашла абзац, но не фразу | Половина баллов потеряна | 🟡 Средняя |
| Модель сказала "ответа нет", а он есть | Полная потеря баллов | 🔴 Критическая |

## 🧠 3. Ключевые понятия (объяснение для новичка)

### Что такое "токен" и почему текст делится на части?

> 💡 **Аналогия:** Представьте, что у вас очень длинный рулон обоев, а у вас есть рамка шириной 50 см. Чтобы рассмотреть весь узор, вы двигаете рамку по рулону шаг за шагом, и каждый раз видите новый кусок.
>
> Нейросеть может обработать **только 512 токенов за раз** (примерно 300-400 слов). Если документ длиннее, его приходится "прокручивать" как рулон — это называется **скользящее окно** (sliding window).

### Что такое "длинный ответ" и "короткий ответ"?

> 💡 **Аналогия:** Представьте, что вы в библиотеке ищете ответ на вопрос.
> - **Длинный ответ** = вы нашли **главу книги**, где обсуждается тема вопроса
> - **Короткий ответ** = вы нашли **конкретное предложение** внутри этой главы с прямым ответом
>
> Иногда вопрос не имеет ответа — тогда оба ответа пустые.

### Что такое BERT?

> 💡 **Аналогия:** Это как **очень начитанный библиотекарь**, который прочитал миллионы книг и умеет понимать контекст слов. Если вы спросите "Что такое банк?", он поймёт по контексту — это речной берег или финансовое учреждение.
>
> Для нашей задачи используется **BERT-large** — самая мощная версия с **340 миллионами параметров** и **24 слоями**.

### Что такое "переобучение" и "утечка данных"?

> 💡 В этой задаче эти понятия не критичны, потому что мы **не обучаем модель заново**, а используем готовые веса. Модель уже обучена на 3.3 миллионах примеров, и наша задача — только правильно её применить.

## ⚙️ 4. Как работает решение (сквозная аналогия + математика)

### 📖 Эксперт №1: "Библиотекарь BERT" (нейросеть)

**Кто это:** Предобученная модель, которая ищет ответ в документе.

**Как он ищет ответ:**

```
Вход:  [CLS] вопрос [SEP] документ [SEP]
       (специальные токены разделяют части)

Выход: для каждого токена — три числа:
  s_i  = оценка "это начало короткого ответа"
  e_i  = оценка "это конец короткого ответа"
  l_i  = оценка "это начало длинного ответа (абзаца)"
```

#### 💡 Простое объяснение:

> Модель читает вопрос и кусок документа. Для каждого слова она ставит три оценки: "насколько вероятно, что это начало ответа", "насколько вероятно, что это конец ответа", "насколько вероятно, что это начало абзаца с ответом". Потом выбираются слова с максимальными оценками.

#### 🎓 Строгое объяснение:

Каждый токен после 24 слоёв трансформера имеет скрытое представление:

```
h_i — вектор из 1024 чисел, для i = 0, 1, ..., L-1
где L — длина последовательности (до 512)
а h_0 соответствует специальному токену [CLS]
```

Три "головы" модели — это три линейных преобразования:

```
Начало короткого ответа:  s_i = W_s · h_i + b_s
Конец короткого ответа:   e_i = W_e · h_i + b_e
Начало абзаца:            l_i = W_l · h_i + b_l

где W_s, W_e, W_l — векторы весов из 1024 чисел
```

Каждая голова — один плотный слой `Dense(1024 → 1)`. Чем больше результат — тем выше уверенность модели.

### 🔍 Механизм внимания внутри BERT

#### 💡 Простое объяснение:

> Когда модель читает слово "пожар", она **смотрит на все остальные слова одновременно**: если рядом "здание" и "911" — это реальный пожар. Если рядом "вечеринка" и "круто" — это метафора.

#### 🎓 Строгое объяснение:

Для каждой из 16 "голов внимания" вычисляется:

```
Attention(Q, K, V) = softmax( Q · K^T / sqrt(64) ) · V

где:
  Q — матрица "запросов" (что я ищу)
  K — матрица "ключей" (что я могу предложить)
  V — матрица "значений" (какую информацию передаю)
  размерность каждой головы = 1024 / 16 = 64
```

Элемент `A[i][j]` показывает, насколько токен `i` должен опираться на токен `j`. Все 16 голов конкатенируются обратно в вектор 1024.

### 🤝 Эксперт №2: "Менеджер по времени" (инженерная часть)

Это самая важная часть решения с точки зрения инженерии.

#### 💡 Простое объяснение:

> Представьте, что вы пишете эссе на экзамене. За 10 минут до конца вы **не начинаете новый абзац**, а дописываете текущий и ставите точку. Лучше сдать неполное, но оформленное эссе, чем не сдать ничего.

#### 🎓 Строгое объяснение:

```
Пусть T0 — момент старта ноутбука.
Определены два порога:

BUDGET         = T0 + 9600 сек   (2 часа 40 минут)
DEADLINE_START = BUDGET - 1200 сек (за 20 минут до дедлайна)

Правила:
  Новый кусок стартует ТОЛЬКО если:
    есть незапущенные куски
    И текущее_время < DEADLINE_START

  Если текущее_время > BUDGET:
    все работающие процессы УБИВАЮТСЯ
    их документы получат пустые ответы
```

## 🚀 5. Три главных "хака", которые дали прирост скорости

### 🔧 Хак №1: Параллельная обработка (главная фишка)

**Проблема:** Оригинальное решение обрабатывало весь тест последовательно — это занимало около часа.

**Решение:** Тест режется на 4 куска и считается параллельно.

```
Тест: 346 документов
Количество процессов: W = min(4, 2 × число_GPU) = 4

Распределение:
  Кусок 0 (документы 1–87)    → GPU 0
  Кусок 1 (документы 88–174)  → GPU 1
  Кусок 2 (документы 175–261) → GPU 0  (второй процесс на той же карте!)
  Кусок 3 (документы 262–346) → GPU 1
```

**Почему два процесса на одну карту?** При инференсе BERT использует GPU не на 100% (примерно 50-60%). Второй процесс использует свободные вычислительные блоки. Памяти хватает: модель занимает ~1.5 ГБ, а на T4 — 16 ГБ.

**Результат:** 17.7 минут вместо ~60 минут. **Ускорение в 3.5 раза.**

### 🔧 Хак №2: Скользящее окно для длинных документов

**Проблема:** Документ может быть длиннее 512 токенов. Модель не может прочитать его целиком.

**Решение:** Документ разбивается на перекрывающиеся окна:

```
Параметры:
  Максимум токенов на вход: 512
  Максимум токенов вопроса: 64
  Специальные токены: 3 ([CLS], [SEP], [SEP])
  Максимум токенов документа в окне: 512 - 64 - 3 = 445
  Шаг скольжения: 256
  Перекрытие: 445 - 256 = 189 токенов

Формула окон:
  Окно 0: [0, 445)
  Окно 1: [256, 701)
  Окно 2: [512, 957)
  ...
  Окно k: [256·k, 256·k + 445)

Количество окон для документа длиной N:
  num_windows = ceil( (N - 445) / 256 ) + 1

Для документа из 100 000 токенов: примерно 390 окон
```

**Зачем перекрытие?** Если ответ находится на границе двух окон, без перекрытия он мог бы потеряться.

### 🔧 Хак №3: Защита от "схлопывания" и ошибок

**Проблема:** Процесс может упасть из-за нехватки памяти или других ошибок.

**Решение:**
```
Если кусок упал (код возврата != 0):
  1. Логируется ошибка
  2. Кусок перезапускается ОДИН раз
  3. Если снова упал → помечается как "неудачный"
  4. Его документы получают пустые ответы
  5. Файл submission.csv остаётся валидным
```

**Инвариант:** финальный файл **всегда** содержит все 692 строки из `sample_submission.csv` (346 документов × 2 типа ответа), даже если часть процессов упала.

## 📐 6. Математика выбора ответа (ключевая часть)

После прогона всех окон через модель у нас есть массивы оценок. Дальше — чистая комбинаторика.

### Шаг 1: кандидаты из каждого окна

```
Для каждого окна берём топ-10 позиций по каждому вектору:
  Топ начал короткого ответа:  10 позиций с максимальными s_i
  Топ концов короткого ответа: 10 позиций с максимальными e_i
  Топ начал абзацев:           10 позиций с максимальными l_i
```

### Шаг 2: перебор пар для короткого ответа

```
Для каждой пары (начало, конец) проверяем фильтры:
  1. начало <= конец
  2. длина ответа <= 30 токенов
  3. оба токена отображаются на реальные слова
     (не [CLS], не [SEP], не паддинг)
  4. оба токена находятся в своём "лучшем окне"

Для каждой валидной пары считается суммарная оценка:
  score(начало, конец) = s_начала + e_конца
```

### Шаг 3: сортировка и выбор лучшего

```
Все валидные пары из всех окон сортируются по убыванию:
  лучшая_пара = argmax по всем парам [ s_i + e_j ]
```

### Шаг 4: решение "пустой ответ или реальный"

**Это самая важная часть.** Модель может сказать "ответа нет".

```
Оценка "пустого ответа" = оценки токена [CLS] (индекс 0):
  score_пусто = s_0 + e_0

Разница:
  разница = score_пусто - (лучший_начальный + лучший_конечный)

Правило:
  если разница > 0:
      ответ = "" (пустая строка, "ответа нет")
  иначе:
      ответ = слова лучшей пары
```

**Смысл:** если оценка `[CLS]` больше суммы оценок лучшего реального ответа → модель уверена, что **ответа в документе нет**. Порог = 0.0 (жёсткое сравнение).

### Шаг 5: преобразование токенов обратно в позиции слов

```
Токенизатор разбивает слова на субтокены:
  Оригинал:  "Толстой написал"
  Субтокены: "То" "##лстой" "напи" "##сал"

Нужен маппинг:
  token_to_orig_map[позиция_субтокена] = позиция_оригинального_слова

Финальный короткий ответ:
  PredictionString = token_to_orig_map[начало] : (token_to_orig_map[конец] + 1)

Почему +1? Потому что правая граница невключительна:
  "224:227" означает слова 224, 225, 226 (три слова)
```

### Шаг 6: поиск длинного ответа среди кандидатов

```
Длинный ответ обязан начинаться с одного из разрешённых абзацев
(список long_answer_candidates из исходного теста).

Для каждого кандидата (начало_абзаца, конец_абзаца):
  если начало_абзаца == предсказанный_токен:
      ответ = "начало_абзаца:конец_абзаца"
      стоп

Если точного совпадения нет — длинный ответ = пустая строка
```

## 🎓 9. Ответы на каверзные вопросы преподавателя

**В: "Почему модель предсказывает позиции, а не сразу текст?"**
О: Потому что модель работает с **фиксированным словарём токенов** (30 522 токена). Она не может генерировать произвольный текст — только указывать на позиции во входном тексте. Это превращает задачу генерации в задачу **классификации позиций**.

**В: "Почему специальный токен [CLS] означает 'нет ответа'?"**
О: `[CLS]` — это токен, который не является частью реального текста. При обучении для примеров **без ответа** правильная позиция начала/конца ставится именно на `[CLS]`. Модель учится: "Если я не вижу ответа, я должна дать максимальную оценку для [CLS]".

**В: "Почему порог для пустого ответа = 0.0?"**
О: Порог 0.0 означает: "Предсказывай пустой ответ только если [CLS] **строго лучше** лучшего реального ответа". Это консервативный подход — мы предпочитаем дать хоть какой-то ответ, чем ошибочно сказать "ответа нет".

**В: "Почему два процесса на одной видеокарте?"**
О: При инференсе модель использует карту не на 100% (примерно 50-60% загрузки). Второй процесс использует свободные вычислительные блоки. Памяти хватает: модель занимает ~1.5 ГБ, а на карте 16 ГБ.

**В: "Что такое токены сегментов и зачем они нужны?"**
О: Это вектор, который говорит модели, какая часть входа — вопрос, а какая — документ:
```
[CLS] вопрос [SEP] документ [SEP]
  0     0      0     1       1
```
Модель использует эту информацию, чтобы по-разному обрабатывать вопрос и контекст.

**В: "Что будет, если тест увеличится до 1000 документов?"**
О: Текущий подход масштабируется линейно. Нужно просто увеличить максимум документов в куске или добавить видеокарт. Архитектура поддерживает любое количество параллельных процессов.

**В: "Можно ли улучшить результат?"**
О: Теоретически да: (1) более современные модели типа Longformer, (2) усреднение нескольких моделей, (3) дополнительное обучение на похожих данных. Но это требует переписывания кода и новых весов.

## 🎯 1. В чём суть задачи?

**Представьте:** вы разрабатываете приложение для грибников. Человек фотографирует гриб, а приложение говорит: "Можно есть" или "Не трогай!".

**Главная сложность:** цена ошибки **асимметрична**.

| Ситуация | Последствие | Серьёзность |
| :--- | :--- | :---: |
| Назвали съедобный гриб ядовитым | Человек пройдёт мимо | 🟡 Низкая |
| Назвали ядовитый гриб съедобным | Человек может умереть | 🔴 Критическая |

Поэтому нам нужна метрика, которая **наказывает за оба типа ошибок одинаково сильно**.

### Почему именно коэффициент Мэтьюса?

#### 💡 Простое объяснение:

> Представьте, что в лесу 99 съедобных грибов и 1 ядовитый. Если модель просто всегда говорит "съедобный", её обычная точность будет 99% — звучит отлично! Но она **пропустила ядовитый гриб**, что смертельно опасно. Коэффициент Мэтьюса наказывает за такие "хитрости".

#### 🎓 Строгое объяснение:

```
Коэффициент Мэтьюса =
    (истинно_положительные × истинно_отрицательные
     - ложно_положительные × ложно_отрицательные)
    /
    корень из произведения четырёх сумм:
    (все_предсказанные_положительные)
    × (все_реальные_положительные)
    × (все_реальные_отрицательные)
    × (все_предсказанные_отрицательные)

Диапазон: от -1 (всё неправильно) до +1 (всё правильно)
0 = случайное угадывание
```

Метрика учитывает **все четыре типа исходов** и инвариантна к дисбалансу классов.
